Conflicts & decisions

Twenty places where this document and the backend disagreed or left something unstated, each with the decision it needed. Nineteen are closed and one is deferred by decision — screen_id, which is defined as development reaches each flow. The last six items are the v1.2 profile-creation re-check. Nothing is left unanswered — every item is either corrected in this document or handed to a named function as a build item.

Per-field privacy ResolvedEngineering

Nothing to decide, as it turns out — the design already has it. A visibility switch reading “Don’t show on my profile” sits on all seven Share some details screens, on Habits and on the age line of the DoB step — nine in total v1.1 counted 8 and called it a checkbox. The backend has only one global visibility switch, so the feature is unbuilt rather than undecided.

backend · one global switchdesign · 9 per-field switches

Outcome: field_display_opted_out and fields_hidden_count stay as specified. Engineering to add per-field privacy; note the semantics — the answer is still used for matching, it just does not surface on the profile.

05

Verification provider ResolvedEngineering

No biometric provider is connected; the stand-in always returns passed, so every result reads pass and the badge cannot be trusted.

decision · to be wired during development

Outcome: Until it lands, the verification funnel is suppressed rather than caveated — a dashboard showing 100% pass is worse than no dashboard.

06

Gender is an enum after all ResolvedProduct

Gender is a four-option single-select on the screen — Woman, Man, Non-binary, Other — so the value is already closed and my “free text” concern was about the backend column, not the UI. The registry now mirrors the screen exactly. Same for orientation, language, education, religion and politics: all closed lists, all read off the kit.

backend · varchar(40)design · 4-option select

Outcome: Registry updated to the real option sets. Engineering to narrow the column to an enum so the two cannot drift. The profile options also moved from Female/Male to Woman/Man: the question asks about gender, and Female/Male are sexes — this also collapses profile and filter onto one vocabulary, since the filter is just the plural of the same values.

07

looking_for is filter state, not a profile field ResolvedProduct

Settled by the screens. Orientation is captured once at profile creation — step 3, single-select — and “who you want to meet” is a search filter where the user picks target genders and the orientations they should have selected. Two different things at two different moments, so nothing is missing from the flow.

profile · orientation, step 3search · meet_gender + meet_orientation

Outcome: looking_for removed from the field_id registry and specified as filter_id on Enums §10. The backend varchar(40) looking_for column is to be dropped — decided, not optional — along with its DTO field and any write path, so nobody stores a profile attribute the product does not collect. The looking_for user property is removed from this document for the same reason. One consequence flagged there: filter payloads carrying orientation are Class 2 about the person filtering.

07b

What “Don’t show on my profile” actually means ResolvedProduct

The toggle appears on all seven Share some details screens and on Habits, and the semantics needed stating before anyone built a report on it.

decision · display suppressed, matching unaffected

Outcome: Recorded on Enums §10. fields_hidden_count is a display-preference metric only — reading it as “data matching cannot see” would be wrong. The inference consequence for orientation-filtered results is accepted.

07c

Opt-out is tracked explicitly; silence means displayed ResolvedProduct

The control is now one checkbox with fixed copy (“Don't display on my profile”), unticked by default, on all nine profile-creation steps. field_display_opted_out carried hidden: bool, which on an opt-out-only event is always true.

decision · one directional event, no boolean

Outcome: Renamed to field_display_opted_out with payload field_id only. No event on untick — the absence of the event for a field means the answer is displayed, so fields_hidden_count is derived from distinct opted-out field_ids at profile completion. A user who ticks and then unticks needs the completion-time state to be authoritative over the event stream.

13

screen_id ownership DeferredProduct

Defined in v1.0 as a design-canvas artboard ID, which couples the warehouse’s primary screen dimension to design-file naming — the first rename breaks it silently.

decision · defer until the concept is development-ready

Outcome: Ids are assigned screen by screen and flow by flow as development proceeds, and added to Enums §7 as they are confirmed. The pattern there stands as the proposal; nothing is enumerated yet.

Consequence to hold: until ids exist, screen_id has no allowed set, so the nine events keyed on it — screen_viewed, error_shown, form_validation_failed and the rest — cannot back a screen-level funnel. Instrument them as each flow is built rather than retrofitting ids afterwards.

15

Age confirmation is not tracked ResolvedProduct

age_confirm_shown and age_confirm_accepted described a popup. The design confirms age inline on the DoB screen, so both events measured a modal that never renders — and the question they were meant to answer is simply whether the step converts.

Outcome: Deleted. dob_submitted is the conversion, age_gate_failed the under-18 case, dob_validation_failed the impossible date, and a Continue tapped with no date entered fires form_validation_failed rule:"required_missing".

A refused Continue is an event, not a dead control ResolvedAnalytics

The kit deliberately keeps Continue live on gated screens and answers a premature tap with a toast — photos under the four-photo minimum being the clearest case. Nothing recorded that tap, so the strongest drop-off signal in profile creation was invisible.

option · a new blocked event per screenchosen · reuse form_validation_failed

Outcome: No new event. form_validation_failed gains a closed rule enum and a step_id, and fires on the refused tap rather than on render. photos_minimum_met keeps its one-time crossing role.

17

Stay reachable carries six toggles; the channel enum listed five and had no value for the calendar consent. There was also no record of the state a user leaves the screen in, only of individual flips.

v1.1 · 5 channels, flips onlyv1.2 · 6 channels + reachability_saved

Outcome: calendar added to channel; consent_changed explicitly carries opt-in as well as opt-out through on: bool; new reachability_saved records channels_on, count and has_phone on save. Consent provenance stays an open question.

18

Hide-rate needs a state mirror, not just an event ResolvedProduct

The per-field control is a switch that defaults to visible, so it can be turned back off again. field_display_opted_out fires on hide only — enough to rank screens by hide-rate, but it cannot answer “how many users hide religion at this moment”, and repeat toggling inflates the count.

option · track the un-hide toochosen · hidden_fields user property

Outcome: Event stays opt-out only, by decision. New user property hidden_fields (Properties §P3) is rewritten in both directions and carries current-state reporting. habits fires once for the whole screen; age becomes a registry value.

What this document still does not cover

Stated plainly, in the same spirit as the glossary’s own closing note.

Photo moderation
Photos carry a review state in the database, and users carry a moderation standing. Neither has an event or a property. Family N covers user reports but not the moderation queue behind them.
Consent provenance
The consent properties record the current state but not when or where it was given. A record of the state without its provenance is not an audit trail.
Biometric consent
A face summary may only be retained after explicit agreement. No event captures that agreement, so there is nothing to prove it was obtained.
Retention
No row states how long any class is kept. Class 2 and 3 need explicit windows before they are collected, not after.
Metric definitions
This is a collection spec. Show-up rate, no-show and late-cancellation are defined by the events that feed them but their formulas live with the score work, which is not built.
